Find the GitHub changes that should have had a second person's approval

Mastyf Authority is a GitHub Action. Once a week it reads your repositories' activity, checks each change against a few rules, and opens an issue listing the force-pushes to main, repositories made public, new admins and other changes that one person should not have been able to make alone.

It changes nothing and blocks nothing. It runs on GitHub's runners, in your account, and sends nothing to us.

  • Set-upone workflow file, about two minutes
  • Costfree; about a minute of Actions time a week

Set it up

Use a private repository for the reports. They name people and repositories, and in a public repository both the issues and the Actions logs are public. The Action refuses to post in a public one.

  1. Create a private repository

    For example mastyf-reports. An existing private repository works too.

  2. Add the workflow

    Save this as .github/workflows/mastyf-authority.yml in that repository.

    name: Mastyf Authority
on:
  schedule: [{ cron: "0 6 * * 1" }]   # Mondays, 06:00 UTC
  workflow_dispatch:
permissions: { contents: read, issues: write }
jobs:
  report:
    runs-on: ubuntu-latest
    steps:
      - uses: mastyf-ai/mastyf-authority/action@main
        with:
          org-token: ${{ secrets.MASTYF_ORG_TOKEN }}

  3. Run it once

    Actions → Mastyf Authority → Run workflow. The first report appears as an issue a minute later. After that it runs every Monday.

Covering the whole organisation

A workflow's own token can only see the repository it runs in. To check every repository, and organisation-level changes such as new owners, give it a read-only token. The first report tells you if it is missing.

  1. Create a fine-grained token

    At github.com/settings/personal-access-tokens/new: resource owner is your organisation, All repositories, repository permission Administration: Read-only (Metadata is added for you) and organisation permission Members: Read-only. Nothing else.

  2. Save it as a secret

    In the reports repository: Settings → Secrets and variables → Actions → New repository secret, named MASTYF_ORG_TOKEN.

  3. Run it again

    The next report covers everything. The token stays in your GitHub: only your workflow uses it. Some organisations need an owner to approve fine-grained tokens; GitHub will ask.

What it checks

Branch activity comes from GitHub's activity log, with who and when. Settings are compared with last week, so for those the report gives the week, not the minute, and usually not the person: GitHub only records that in the audit log of its Enterprise plan.

Privacy

Everything happens inside your GitHub account.

The workflow runs on GitHub's runners with the permissions in its file: read this repository's contents, write issues. With an organisation token it can also read settings and membership, never write. It reads activity and settings through GitHub's API; it does not read code.

It keeps nothing anywhere except the report issue itself. To spot changes, last week's settings are stored, compressed, in a hidden comment in the previous report. Delete the issues and the history is gone.

Mastyf Labs receives no data, no telemetry and no token. Privacy policy.

Questions

Does it ever block anything?
No. It reports what Mastyf Authority would have done. If you want risky changes to actually wait for a second person, that is what Mastyf Authority itself does, inside your own infrastructure. We are offering a free 60-day pilot to our first three design partners.
How does it decide what is unusual?
Fixed rules for the clear cases (rewriting a protected branch, making a repository public). For the rest it compares each change with that person's own activity over the previous 90 days, plus a small risk model the Action trains on the runner from synthetic examples.
Why does it need issues: write?
To open the weekly report. It writes nothing else.
What does it miss?
Anything GitHub does not expose outside its Enterprise audit log: who viewed or cloned what, and who changed a setting. It also cannot see a change that was made and undone within the same week.
How do I stop it?
Delete the workflow file, or disable it under Actions.
